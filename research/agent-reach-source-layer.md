# Agent Reach as OpenRecruit's source-access layer

_Research date: 2026-08-22. Agent Reach revision inspected: [`93ae1d18`](https://github.com/Panniantong/Agent-Reach/tree/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d) (current `main` at research time). “Verified” below means supported directly by first-party source code, repository documentation, or platform policy; “inference” is labeled._

## Decision

**Do not adopt Agent Reach as OpenRecruit's source-access abstraction.** It is a useful, fast-moving catalog and workstation bootstrapper for upstream tools, but it is intentionally an installer, doctor, and command-routing skill—not a runtime connector API. It does not give OpenRecruit a normalized result contract, provenance envelope, scheduling/checkpoint model, durable cursor semantics, or a consistent retry/rate-limit policy. Its authenticated X, LinkedIn, and Reddit routes also rely on browser sessions, reverse-engineered endpoints, or website automation that conflict with those platforms' current first-party automation/access policies.

Use the investigation this way:

1. **Adopt directly, behind OpenRecruit-owned adapters:** RSS/Atom via `feedparser`; GitHub via the official `gh` CLI/API; broad-web retrieval/search via Jina Reader and Exa only after accepting their hosted-service data and quota boundaries.
2. **Do not ship by default:** Agent Reach's `twitter-cli`, OpenCLI X/LinkedIn/Reddit adapters, `mcp-server-linkedin`, or `rdt-cli` routes. Consider only a separately approved experimental mode after policy/legal review, explicit Candidate consent, dedicated accounts, and a documented account-risk boundary.
3. **Use Agent Reach only as reference material or an optional developer bootstrapper:** copy neither its routing claims nor `active_backend` result into OpenRecruit's truth model. Pin and qualify every selected upstream independently.

## What Agent Reach actually is

Verified:

- Agent Reach describes itself as a “capability layer” that selects, installs, diagnoses, and routes to ordered upstream backends; after setup, the agent calls those upstream commands directly. Its own `AgentReach` class exposes health checks, not search/read operations, and its current CLI exposes setup, install, configure, doctor, skill, update, watch, format, transcription, and uninstall commands—not a common source-query API. ([architecture contract](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/channels/base.py), [core](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/core.py), [CLI](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/cli.py))
- A channel is chiefly URL matching plus a health check. Ordered backends can be overridden, and the first actually usable backend should become active. Sensitive channels frequently return `warn` with no active backend because `doctor` intentionally avoids commands that could read/refresh browser cookies or write state. ([channel contract](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/channels/base.py), [X check](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/channels/twitter.py), [GitHub check](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/channels/github.py), [maintainer explanation](https://github.com/Panniantong/Agent-Reach/issues/566#issuecomment-5202781217))
- Therefore a successful installation or a `doctor` warning is not evidence that a real query returns substantive content. The project explicitly encountered this distinction during live channel testing. ([issue #566](https://github.com/Panniantong/Agent-Reach/issues/566))

Inference: Agent Reach can shorten exploratory setup, but making it the source layer would leave core OpenRecruit behavior dependent on mutable prose instructions and heterogeneous subprocess output. OpenRecruit still needs its own connector interface and acceptance tests.

## Install, runtime, licensing, and maintenance

### Install and runtime

Verified:

- The Python package declares Python 3.10+, version 1.5.0, and direct dependencies including `requests`, `feedparser`, YAML/Rich/logging libraries, and `yt-dlp`; browser/MCP/cookie support is optional. It is installed from the GitHub archive with `pipx` or a virtual environment rather than from the same-named PyPI package. ([package manifest](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/pyproject.toml), [install guide](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/docs/install.md))
- `agent-reach install` is check-only by default. `--system` explicitly authorizes external/global installs and configuration writes; depending on channels it can invoke Homebrew, npm, pipx, `mcporter`, and skill installation under user-level agent directories. `--dry-run` previews those actions. ([install guide](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/docs/install.md), [installer implementation](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/cli.py))
- Relevant transitive runtimes are substantial and heterogeneous: Node.js/mcporter for Exa MCP; Node.js 20+, a local daemon, Chrome/Chromium, and an extension for OpenCLI; and `uvx`, Patchright Chromium, and an MCP process for LinkedIn. ([Agent Reach install guide](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/docs/install.md), [OpenCLI setup](https://github.com/jackwener/OpenCLI#quick-start), [LinkedIn MCP setup](https://github.com/stickerdaniel/linkedin-mcp-server#-uvx-setup-recommended---universal))
- A clean local installation from the inspected revision failed during this research because the manifest requires `yt-dlp[default]>=2026.07.04`, while the PyPI index visible to this environment advertised 2025.10.14 as latest. The open report is disputed by a commenter who observed 2026.7.4 in a different environment, so the durable conclusion is **index/environment-dependent installation is currently unresolved**, not that the version can never exist. ([manifest](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/pyproject.toml), [PyPI release index](https://pypi.org/project/yt-dlp/#history), [issue #601](https://github.com/Panniantong/Agent-Reach/issues/601))

### License and maintenance

Verified:

- Agent Reach itself is MIT-licensed. That license does not relicense its separately invoked tools or hosted services. ([license](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/LICENSE))
- `twitter-cli`, OpenCLI, LinkedIn MCP, and Jina Reader identify as Apache-2.0; GitHub CLI is MIT. The pinned `public-clis/rdt-cli` repository has **no detected license file or GitHub license designation**, so it should not be redistributed or incorporated without clarification. ([twitter-cli license](https://github.com/public-clis/twitter-cli/blob/main/LICENSE), [OpenCLI license](https://github.com/jackwener/OpenCLI/blob/main/LICENSE), [LinkedIn MCP license](https://github.com/stickerdaniel/linkedin-mcp-server/blob/main/LICENSE), [Jina Reader license](https://github.com/jina-ai/reader/blob/main/LICENSE), [GitHub CLI license](https://github.com/cli/cli/blob/trunk/LICENSE), [rdt-cli repository](https://github.com/public-clis/rdt-cli))
- The repository was created in February 2026, published seven tagged releases through v1.5.0 by June, and continued receiving main-branch fixes through August. Contribution history is strongly concentrated in the owner (318 commits attributed on GitHub versus 9 for the next contributor at research time), and the repository reported 96 open issues. This is strong activity but a material bus-factor and triage-risk signal. ([repository metadata](https://api.github.com/repos/Panniantong/Agent-Reach), [releases](https://github.com/Panniantong/Agent-Reach/releases), [contributors](https://github.com/Panniantong/Agent-Reach/graphs/contributors), [commit history](https://github.com/Panniantong/Agent-Reach/commits/main/))
- Released v1.5.0 and `main` differ materially: later hardening changed doctor truthfulness, credential boundaries, URL handling, and platform guidance. Using `main` gains fixes but loses release reproducibility; using v1.5.0 misses those fixes. ([v1.5.0 release](https://github.com/Panniantong/Agent-Reach/releases/tag/v1.5.0), [post-release commits](https://github.com/Panniantong/Agent-Reach/commits/main/))

The MCP server verifies company profiles/posts/employees, company search, job search/saved jobs/details, people search, and profiles. Agent Reach is unnecessary at runtime. |
| **RSS/Atom** | `feedparser` is a direct Python dependency and supports RSS variants, Atom, CDF, JSON feeds, and common extensions. ([channel](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/channels/reddit.py), [rdt-cli README](https://github.com/public-clis/rdt-cli), [OpenCLI commands](https://github.com/jackwener/OpenCLI#built-in-commands)) | There is no zero-config route. ## Authentication and security boundaries

Verified strengths in Agent Reach itself:

- Default installation is read-only/check-only; mutation requires `--system` and has dry-run support. Credentials are stored under `~/.agent-reach/config.yaml`; writes are atomic, owner-only (`0600` on POSIX), and reject symlinked paths. Diagnostic output masks credential-like keys. ([config implementation](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/config.py), [doctor](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/doctor.py))
- The web wrapper rejects userinfo, private/non-global literal IPs, local hostnames, malformed schemes, and oversized responses. The project publishes a security policy covering auth bypass, RCE, path traversal, SSRF, injection, and sensitive-data exposure. ([URL utility](https://github.com/Panniantong/Agent-Reach/blob/93ae1d18c37b707dec053c7c4f9d91cd8ef8943d/agent_reach/utils/url.py), [security policy](https://github.com/Panniantong/Agent-Reach/security/policy))

Material residual boundaries:

- Agent Reach's local file protection does not reduce the power of session cookies. X/Reddit cookies and the LinkedIn/OpenCLI browser bridge can act as the Candidate and expose whatever the signed-in browser can see. Upstreams may read browser stores, persist their own profiles, refresh sessions, or perform write actions; Agent Reach does not mediate calls after installation.
- OpenCLI is a local daemon plus extension capable of navigation, DOM extraction, network interception, filling forms, and clicks across a logged-in browser. Its built-in adapters include write actions. This is a broad browser-control trust boundary, not a narrow read connector. ([OpenCLI operation](https://github.com/jackwener/OpenCLI#how-it-works), [commands](https://github.com/jackwener/OpenCLI#built-in-commands))
- `mcp-server-linkedin@latest` enables automatic updates; its own docs tell agents to obtain confirmation before enabling that. An unpinned runtime is inappropriate for reproducible OpenRecruit ingestion. ([LinkedIn setup](https://github.com/stickerdaniel/linkedin-mcp-server#-uvx-setup-recommended---universal))
- `--system` executes multiple external package managers and installs agent skills. That is acceptable as an explicitly reviewed workstation bootstrap, not as an application startup behavior.

## Provenance and failure contract OpenRecruit still needs

Verified: Agent Reach returns health status/message/backend metadata, while actual content remains in tool-specific formats. Some upstreams expose excellent source fields, but there is no cross-source guarantee and no record of which exact command, connector revision, auth context, query, or fallback produced a Signal.

Inference/recommendation: every OpenRecruit adapter should emit an immutable evidence envelope containing at least:

- source family and connector/version;
- canonical origin URL and platform-native ID;
- Discovery Strategy query/filter and the exact retrieval method;
- `observed_at`, provider-published/updated time, and freshness/cache controls;
- Candidate account/profile identifier without secrets;
- raw-response hash plus a bounded raw snapshot or durable cache reference;
- normalized title/text/author/company/job fields;
- HTTP/tool status, retry/rate-limit state, completeness warnings, and fallback chain;
- policy/authorization mode used for the retrieval.

Retries should live in each OpenRecruit adapter, not in Scouts: honor GitHub rate headers; use RSS conditional requests and terminal `410`; recognize Jina/Exa `429`, cache, timeout, truncation, and anti-bot output; never silently convert auth/challenge/empty-parser failures into “no Signals.”

## POC source portfolio resulting from this research

Recommended initial portfolio:

1. RSS/Atom feeds.
2. GitHub public repositories, issues, releases, and activity through an authenticated read-only Candidate-owned `gh` session/API.
3. Broad-web search through Exa and page retrieval through Jina, with provider/caching provenance and per-domain policy checks.
4. Direct public career pages and ATS feeds discovered through those mechanisms where their site terms and robots/access controls permit it.

Defer LinkedIn, X, and Reddit until an approved API/access route and its economics are known. Technical success through a browser cookie is not sufficient evidence of a supportable source connector.

## Newly surfaced questions

1. Is the POC allowed to exclude LinkedIn, X, and Reddit entirely, or is one of them a hard product requirement that justifies official API/vendor procurement?
2. Will broad-web URLs and page contents be permitted to leave the machine for Jina/Exa processing, or must OpenRecruit self-host/fetch locally?
3. What retention/deletion rules apply to raw public evidence, especially personal profile/post data that later disappears?
4. Should GitHub discovery be limited to repository/project evidence, excluding personal-data aggregation and all outreach use?
5. What connector acceptance gate is required—live smoke tests with substantive-content assertions, pinned versions, policy review date, and failure fixtures are recommended.
